## 2026-09-07 — Engine pinned to UE 5.8; build toolchain is VS2022, not VS2026
**Decision:** `EngineAssociation` is `5.8` (per §0 of the scaffold, log the exact version at kickoff — done here). C++ project-file generation must target **Visual Studio 2022**, installed alongside whatever newer VS version is on a given machine — do not rely on the newest installed VS.
**Reason:** UE 5.8's `UnrealBuildTool` doesn't recognize Visual Studio 2026 (v18) as a supported project-file format. With only VS2026 installed, project generation failed with `Unexpected ProjectFileFormat 'Default'` (UBT detects the installed IDE, can't map it to a known format, and falls back to the literal unhandled string `"Default"`). Installing VS2022 side-by-side (Community edition, "Game development with C++" workload) resolved it.
**Who it affects:** game-director (build order assumes C++ compiles), anyone setting up the project on a new machine — check installed VS version before assuming project generation will "just work" on the newest VS available. `Config/DefaultEditorPerProjectUserSettings.ini` is now gitignored so a machine's resolved IDE/editor preference doesn't get committed and break other machines the way this did.

## 2026-09-07 — APvPDeathmatchGameMode drives its own match-state machine (AGameModeBase has none)
**Decision:** `APvPDeathmatchGameMode::SetMatchState()` is a small hand-rolled state setter that writes `EPvPMatchState` (`Source/PvPArena/Core/PvPMatchState.h`) onto `APvPDeathmatchGameState::CurrentMatchState`, rather than overriding `HandleMatchIsWaitingToStart`/`HandleMatchHasStarted`/`HandleMatchHasEnded`.
**Reason:** Those `Handle*` hooks only exist on the fuller `AGameMode`, not on `AGameModeBase` — which is the base class §2.1 of the scaffold explicitly calls for. Assumed otherwise while writing the B3 skeleton; the compiler caught it (`C2039: is not a member of 'AGameModeBase'`) before it shipped. Switching to `AGameMode` would have been the "easy" fix but silently pulls in its lobby/timeout machinery, which isn't a decision to make unilaterally.
**Who it affects:** Phase E (win condition / `EndMatch`) — call `SetMatchState(EPvPMatchState::InProgress)` / `SetMatchState(EPvPMatchState::Ending)` from there rather than expecting `AGameMode`-style virtuals to fire.

## 2026-09-08 — Any non-interactive UMG overlay must set Visibility(HitTestInvisible)
**Decision:** `UPvPHUDWidget`'s root `SOverlay` explicitly sets `.Visibility(EVisibility::HitTestInvisible)`. Applies to any future pure-display widget added to the viewport during active gameplay (as opposed to the tutorial/result screens, which are meant to capture input).
**Reason:** The player could not fire at all after the HUD shipped — confirmed via log that only the AI bot (which calls `Fire()` directly in C++, bypassing input) ever fired; the player's identically-bound Left Click never reached `HandleFireInput`. Root cause: Slate widgets default to `EVisibility::Visible`, which is hit-testable. A full-screen `SOverlay` with that default silently swallows every mouse click before it reaches Enhanced Input, even though it contains nothing but display text and was never meant to be interactive. Keyboard input was unaffected (keyboard routing is focus-based, not hit-test/position-based), which is why WASD/Q/V kept working while only Left Click silently died — a useful diagnostic signature if this class of bug recurs.
**Who it affects:** Any future HUD/overlay work shown during live gameplay (ammo counters, kill feed, minimap, etc.) — default to `HitTestInvisible` unless the widget genuinely needs to receive clicks.

## 2026-09-08 — QA pass (code inspection) caught 4 real P0s in the Milestone 2 wiring
**Decision:** Fixed all four without argument — a from-source QA report (no live PIE session available to the reviewer) correctly traced each to the actual cause: (1) the bot's `TargetAcquiredTimeSeconds` was only ever set once at spawn, so its engagement delay had nothing to reset against on player respawn and it could fire immediately; (2) the level had exactly one `PlayerStart`, so player and bot respawn could land on top of each other; (3) `UPvPWeaponComponent::Fire()` never decremented `CurrentAmmo`, so the HUD ammo readout and "empty weapon" state were fictional; (4) "Play Again" reloaded the level, which — since `BeginPlay` always shows the main menu — meant it silently returned to the menu instead of starting a rematch.
**Reason:** All four block calling the slice actually playable end-to-end, which was the explicit bar this QA pass was testing against.
**Who it affects:** `APvPCharacter::HandleRespawn()` is now public and safe to call on a living character, not just a corpse — anything building on top of it (e.g. a future real respawn-selection system) should preserve that. Two `PlayerStart`s now exist in `Lvl_PracticeRing`, tagged `PlayerSpawn`/`BotSpawn` via `APlayerStart::PlayerStartTag` — any future level for this mode needs the same two tagged starts, or spawn selection silently falls back to "any start found first."

## 2026-09-08 — QA pass 2 (code inspection only) caught 2 more real bugs in HandleRespawn/AI fire

**Decision:** Fixed both. (1) `HandleRespawn()` never cleared `RespawnTimerHandle` — `RestartMatch()`'s in-place rematch calls `HandleRespawn()` directly, but if a death happened just before "Play Again," the original death-triggered timer was still pending and fired again a few seconds into the new match, re-teleporting/re-arming everyone a second time. Now `HandleRespawn()` clears that timer as its first action. (2) `HandleRespawn()` reset health but never ammo, so dying or rematching with a partially/fully empty clip carried the empty clip into the next life — now it re-calls `WeaponComponent->EquipWeapon(WeaponComponent->WeaponData)`, which refills `CurrentAmmo` to max as a side effect of re-equipping the same weapon. Also fixed `APvPAIController::Tick()`: the bot had no reload and shared the same ammo gate as the player, but nothing ever pressed "Q" for it, so an emptied bot would stand at its target attempting to fire nothing for the rest of the match — it now calls `Weapon->CycleWeapon()` instead of `Weapon->Fire()` whenever its current weapon is out of ammo.
**Reason:** A second from-source QA pass (still no PIE access on the reviewing side) traced both from the existing respawn/fire code paths; both were confirmed by direct inspection here before fixing. The QA pass's third hypothesis — that `UPvPHUDWidget` itself (the `UUserWidget`/`SObjectWidget` wrapper, not just its root `SOverlay`) needed `SetVisibility(HitTestInvisible)` to stop swallowing the player's Left Click — was NOT applied: `HandleDismissTutorial`/`HandlePlayAgain` both call `SetInputMode(FInputModeGameOnly())` before the HUD is even created, and `FInputModeGameOnly` pins Slate focus to the viewport widget itself, bypassing UI hit-testing for input routing entirely — so the HUD's own hit-test visibility shouldn't be able to block gameplay input regardless of its value. Diagnostic logging (commit `9494032`, still in place) will confirm directly on the next PIE session whether Enhanced Input ever calls `HandleFireInput` at all; changing widget visibility speculatively without that evidence risks masking the real cause.
**Who it affects:** Anyone touching `HandleRespawn()` — it's now the single place that resets health, ammo, and pending timers together for both player and bot, on death and on rematch; don't reset those individually elsewhere. AI fire logic assumes `CycleWeapon()` is always safe to call mid-fight (it is — see `EquipWeapon`).

## 2026-09-10 — Fire-input bug resolved; root cause never fully confirmed
**Decision:** The player-can't-fire bug (reported repeatedly since the practice-vs-AI milestone shipped) is fixed. `APvPCharacter`/`APvPPlayerController` now trigger `UPvPWeaponComponent::Fire()` off the legacy raw-key path (`BindKey` for LMB/F on the Character, plus continuous `PlayerTick` polling of `IsInputKeyDown`/Slate's pressed-mouse-buttons on the Controller) instead of relying on Enhanced Input's `IA_Fire` action. `UPvPWeaponComponent::Fire()` also now calls `PerformServerTrace` directly when the owner `HasAuthority()`, rather than always going through the `ServerFire` RPC, since a Server RPC on a listen-server-hosted pawn with no remote connection was suspected of being silently dropped.
**Reason:** Extensive live-PIE diagnosis (logging every Enhanced Input trigger state, comparing `IA_Fire` against known-working `IA_Jump`/`IA_Move`, testing alternate keys, checking for duplicate assets, checking `bShouldFlushPressedKeysOnViewportFocusLost`) proved conclusively that **no action bound to a mouse button ever reached Enhanced Input's trigger evaluation in this project/environment** — `IA_Jump` mapped to LeftMouseButton (alongside its already-working SpaceBar mapping) never fired either. Multiple plausible-sounding fixes along the way (`IA_Fire` missing a Trigger; the focus-flush setting) were real, correct fixes for real problems they identified, but neither actually resolved the underlying issue, and the true mechanism was never pinned down. A parallel session (Cursor, the QA/bug-finder tool set up earlier) reached a working fix independently by bypassing Enhanced Input for Fire entirely — pragmatic given how thoroughly the EI path was proven broken here, even without a root cause.
**Who it affects:** Anyone adding new mouse-button-driven actions in this project should not assume Enhanced Input will deliver them — verify in a live PIE session before relying on it, and prefer the raw `BindKey`/`IsInputKeyDown` pattern now used for Fire if it doesn't. `IA_Fire`'s Enhanced Input binding (`HandleFireInput`, bound to `ETriggerEvent::Triggered`) and its `IMC_Default` mapping are left in place as a harmless redundant path in case Enhanced Input's mouse-button handling ever starts working in some environment — `Fire()`'s own cooldown gate makes a duplicate call from both paths in the same frame a no-op, not a double-fire. Diagnostic-only code from the investigation (Enhanced Input per-trigger-state logging, `HasMappingContext` logging, "FIRE BUILD" debug banners in the tutorial/HUD/on-screen text) has been removed now that the fix is confirmed live in PIE (player fires all three weapons, ammo decrements, hits register).
