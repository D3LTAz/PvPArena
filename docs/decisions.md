## 2026-09-07 — Engine pinned to UE 5.8; build toolchain is VS2022, not VS2026
**Decision:** `EngineAssociation` is `5.8` (per §0 of the scaffold, log the exact version at kickoff — done here). C++ project-file generation must target **Visual Studio 2022**, installed alongside whatever newer VS version is on a given machine — do not rely on the newest installed VS.
**Reason:** UE 5.8's `UnrealBuildTool` doesn't recognize Visual Studio 2026 (v18) as a supported project-file format. With only VS2026 installed, project generation failed with `Unexpected ProjectFileFormat 'Default'` (UBT detects the installed IDE, can't map it to a known format, and falls back to the literal unhandled string `"Default"`). Installing VS2022 side-by-side (Community edition, "Game development with C++" workload) resolved it.
**Who it affects:** game-director (build order assumes C++ compiles), anyone setting up the project on a new machine — check installed VS version before assuming project generation will "just work" on the newest VS available. `Config/DefaultEditorPerProjectUserSettings.ini` is now gitignored so a machine's resolved IDE/editor preference doesn't get committed and break other machines the way this did.

## 2026-09-07 — APvPDeathmatchGameMode drives its own match-state machine (AGameModeBase has none)
**Decision:** `APvPDeathmatchGameMode::SetMatchState()` is a small hand-rolled state setter that writes `EPvPMatchState` (`Source/PvPArena/Core/PvPMatchState.h`) onto `APvPDeathmatchGameState::CurrentMatchState`, rather than overriding `HandleMatchIsWaitingToStart`/`HandleMatchHasStarted`/`HandleMatchHasEnded`.
**Reason:** Those `Handle*` hooks only exist on the fuller `AGameMode`, not on `AGameModeBase` — which is the base class §2.1 of the scaffold explicitly calls for. Assumed otherwise while writing the B3 skeleton; the compiler caught it (`C2039: is not a member of 'AGameModeBase'`) before it shipped. Switching to `AGameMode` would have been the "easy" fix but silently pulls in its lobby/timeout machinery, which isn't a decision to make unilaterally.
**Who it affects:** Phase E (win condition / `EndMatch`) — call `SetMatchState(EPvPMatchState::InProgress)` / `SetMatchState(EPvPMatchState::Ending)` from there rather than expecting `AGameMode`-style virtuals to fire.

## 2026-09-08 — Practice-vs-AI milestone complete
**Decision:** Treating the single-player practice build (the 2026-09-07 pivot above) as done for now: tutorial/start overlay → match with a HUD (health/ammo/weapon/score) → first-to-3-kills win condition → victory/defeat screen → replay. Not resuming the original multiplayer Milestone 1 scope at this time.
**Reason:** Requested directly ("finish milestone one," clarified to mean the practice build, not the parked multiplayer scope). Playtesting surfaced and fixed several real bugs along the way worth noting for anyone touching this code next: `IMC_Default`/`IMC_MouseLook` had zero key mappings from project creation (silent — WASD/fire never worked, only raw-bound keys like F11/Q did); `HandleDeath`'s "respawn" was a log-only stub that permanently soft-locked the player on death; the AI bot could kill the player in ~1s by engaging at point-blank range with no warm-up; `FInputModeUIOnly` silently prevents `InputComponent::BindKey` from firing, so widget-dismiss keys must be handled in the widget itself (`NativeOnKeyDown`), not the controller; and `FirstPersonCamera`'s height used `BaseEyeHeight` as an offset from the capsule's *center* instead of its *base*, sitting the camera too low. All fixed and pushed (see commit history `a4a74c0`..`92af473`).
**Who it affects:** Anyone resuming multiplayer work later — the GameState/PlayerState/GameMode/Character/HealthComponent/WeaponComponent framework is unchanged and reusable; only APvPPracticeGameMode, the AI controller, the tutorial/HUD/result widgets, and Lvl_PracticeRing are practice-mode-specific and would need swapping out (or kept as a permanent training mode alongside real PvP).

## 2026-09-08 — Any non-interactive UMG overlay must set Visibility(HitTestInvisible)
**Decision:** `UPvPHUDWidget`'s root `SOverlay` explicitly sets `.Visibility(EVisibility::HitTestInvisible)`. Applies to any future pure-display widget added to the viewport during active gameplay (as opposed to the tutorial/result screens, which are meant to capture input).
**Reason:** The player could not fire at all after the HUD shipped — confirmed via log that only the AI bot (which calls `Fire()` directly in C++, bypassing input) ever fired; the player's identically-bound Left Click never reached `HandleFireInput`. Root cause: Slate widgets default to `EVisibility::Visible`, which is hit-testable. A full-screen `SOverlay` with that default silently swallows every mouse click before it reaches Enhanced Input, even though it contains nothing but display text and was never meant to be interactive. Keyboard input was unaffected (keyboard routing is focus-based, not hit-test/position-based), which is why WASD/Q/V kept working while only Left Click silently died — a useful diagnostic signature if this class of bug recurs.
**Who it affects:** Any future HUD/overlay work shown during live gameplay (ammo counters, kill feed, minimap, etc.) — default to `HitTestInvisible` unless the widget genuinely needs to receive clicks.

## 2026-09-08 — QA pass (code inspection) caught 4 real P0s in the Milestone 2 wiring
**Decision:** Fixed all four without argument — a from-source QA report (no live PIE session available to the reviewer) correctly traced each to the actual cause: (1) the bot's `TargetAcquiredTimeSeconds` was only ever set once at spawn, so its engagement delay had nothing to reset against on player respawn and it could fire immediately; (2) the level had exactly one `PlayerStart`, so player and bot respawn could land on top of each other; (3) `UPvPWeaponComponent::Fire()` never decremented `CurrentAmmo`, so the HUD ammo readout and "empty weapon" state were fictional; (4) "Play Again" reloaded the level, which — since `BeginPlay` always shows the main menu — meant it silently returned to the menu instead of starting a rematch.
**Reason:** All four block calling the slice actually playable end-to-end, which was the explicit bar this QA pass was testing against.
**Who it affects:** `APvPCharacter::HandleRespawn()` is now public and safe to call on a living character, not just a corpse — anything building on top of it (e.g. a future real respawn-selection system) should preserve that. Two `PlayerStart`s now exist in `Lvl_PracticeRing`, tagged `PlayerSpawn`/`BotSpawn` via `APlayerStart::PlayerStartTag` — any future level for this mode needs the same two tagged starts, or spawn selection silently falls back to "any start found first."
