# PvP Arena — Stage 1 / Milestone 1 Technical Scaffold Plan

**Author:** game-director
**Status:** Ready to execute
**Scope guard:** Multiplayer deathmatch, 1v1/2v2/3v3, one graybox map (3v3-sized), one starting weapon, minimal format-picker matchmaking (no skill-based matching). **Why one module, not Lyra-style modular plugins:** Lyra ships as a constellation of Game Feature plugins (`ShooterCore`, `LyraGame`, etc.) behind the Game Features / Modular Gameplay plugins. That architecture earns its cost at Lyra's scale (many game modes, hot-pluggable content, a team). At Milestone 1 scale — one map, one mode, one weapon, one developer — it's pure overhead: more Build.cs files, more plugin descriptors, more indirection, zero payoff yet. **Recommendation: single `PvPArena` module now; split into plugins only when a second, meaningfully different game mode is on deck and modularity would prevent duplication.** This is a scope-protection call, logged here rather than left open — revisit explicitly if that trigger condition is hit.

**Lyra itself is not vendored into this repo.** Download/create it as its own separate UE5 project (via Epic Games Launcher / Fab), open it in a second editor instance, and read specific systems as reference:
- `Source/LyraGame/Weapons/` — hitscan/projectile fire pattern, damage pipeline
- `Source/LyraGame/GameModes/` — `ALyraGameMode`/`ALyraGameState` match-state flow
- `Source/LyraGame/Character/` — replicated character setup, health component pattern

Do not copy files wholesale — Lyra's classes assume the Gameplay Ability System and Game Features, neither of which is in scope for M1. Port *patterns* (how they structure server RPCs, how they replicate health, how match state transitions), not code.

## 2. C++ Module & Class Breakdown

### 2.0 Module

One module, `PvPArena`, `Type: Runtime`, `LoadingPhase: Default`. Dependencies: `Core, CoreUObject, Engine, InputCore, EnhancedInput, NetCore`. Add `OnlineSubsystem` / `OnlineSubsystemNull` only when Matchmaking (§2.4) needs them.

### 2.1 Core / Match Framework

| Class | Base | Responsibility |
|---|---|---|
| `APvPDeathmatchGameMode` | `AGameModeBase` | Server-only. Owns match flow: waiting-to-start → in-progress → ending. Reads the format (1v1/2v2/3v3) selected during matchmaking, assigns players to teams, picks team-tagged `PlayerStart`s, starts respawn timers, evaluates the win condition (score cap or time limit — pick score cap for M1, simpler), calls `EndMatch`. |
| `APvPDeathmatchGameState` | `AGameStateBase` | Replicated. Team scores (array of 2 ints for M1 — deathmatch is 2 teams regardless of format), match clock, current `EMatchFormat`. Read by HUD on all clients. |
| `APvPPlayerState` | `APlayerState` | Replicated. Kills, deaths, team index. |
| `APvPPlayerController` | `APlayerController` | Input possession, HUD ownership, routes "ready"/format-picker UI events to the matchmaking subsystem. |
| `UPvPGameInstance` | `UGameInstance` | Holds the matchmaking subsystem (subsystems auto-attach, but this is the natural home for any session-lifetime state that isn't a subsystem). |

**Replication note:** `AGameModeBase` never replicates (server-only by design) — all client-visible match state lives on `APvPDeathmatchGameState`. This is standard UE pattern, called out here because getting it backwards (putting replicated properties on GameMode) is the single most common new-UE-dev mistake and would silently break clients seeing scores/timers.

### 2.2 Character & Health

| Class | Base | Responsibility |
|---|---|---|
| `APvPCharacter` | `ACharacter` | Standard `UCharacterMovementComponent` for M1 (no custom movement — that's a Stage 2+ conversation if movement tech becomes a differentiator). Owns `UPvPWeaponComponent` and `UPvPHealthComponent`. |
| `UPvPHealthComponent` | `UActorComponent` | Replicated `CurrentHealth`/`MaxHealth`. `ServerApplyDamage(float Amount, AController* Instigator)` — server-authoritative only, no client can reduce its own health. Broadcasts `OnDeath` delegate consumed by the GameMode for respawn + scoring. |

### 2.3 Weapon System + Hit Registration + Lag Compensation

This is the architecturally load-bearing piece of M1 — get this right and every future weapon/map is additive; get it wrong and it's a rewrite.

| Class | Base | Responsibility |
|---|---|---|
| `UPvPWeaponData` | `UPrimaryDataAsset` | Blueprint-authorable config: damage, fire rate, max range, hitscan spread, ammo pool, mesh/VFX/SFX soft references. One data asset instance = the M1 starting weapon. This is the "config in Blueprints" half of the stack split — no weapon numbers live in C++. |
| `UPvPWeaponComponent` | `UActorComponent` (replicated) | Attached to `APvPCharacter`. Owns current ammo/cooldown state. `Fire()` called locally on the owning client → plays cosmetic muzzle FX immediately (unreliable, non-authoritative, purely for feel) → sends `ServerFire(FVector_NetQuantize Origin, FVector_NetQuantizeNormal Direction, float ClientTimestamp)` RPC. Server validates fire rate/ammo, asks `UPvPLagCompensationComponent` for a rewound trace, applies damage via `UPvPHealthComponent::ServerApplyDamage`, then `NetMulticast` a "confirmed hit" event so all clients see the same tracer/impact FX — this is the shared source of truth clients render against, not their own prediction. |
| `UPvPLagCompensationComponent` | `UActorComponent`, one per `APvPCharacter`, server-only logic | Every fixed tick (recommend a dedicated ~33ms interval, not every frame — tune during Phase D) pushes the actor's current hit-relevant transform (capsule location/rotation + a head-offset sphere; **not** full skeletal hitboxes — that's a scope trap, see below) into a fixed-size ring buffer covering the last ~1 second. On `ServerFire`, computes rewind time from the firing player's current ping (`APlayerState::GetPingInMilliseconds()`), clamped to a configurable max (recommend 300ms — prevents "shot behind the wall 3 seconds ago" abuse), interpolates each other player's buffered transforms to that time, performs the line trace against the rewound positions, then restores real positions. Exposes one entry point: `static bool RewindAndTrace(UWorld*, const FVector& Origin, const FVector& End, float RewindSeconds, FHitResult& OutHit)`. |

**Explicit scope guard:** hitboxes for lag compensation are **capsule + head sphere**, not per-bone skeletal mesh hitboxes. Bone-accurate hit detection is a real feature many shooters have, but it's a materially larger system (bone transform recording, per-bone collision, headshot-multiplier balancing) than M1's "one starting weapon, prove the pipeline works" goal needs. If Daniel wants bone-accurate hitboxes, that's priced separately and kicked to studio-director before starting — not built quietly here.

**Weapon is hitscan, not projectile**, for M1: simpler trace-and-rewind logic, and it matches the CS/Valorant reference point better than a projectile weapon would as the *first* weapon. Projectile weapons (grenades, rockets) are additive later without touching this architecture.

### 2.4 Matchmaking (format-picker, no skill-based matching)

| Class | Base | Responsibility |
|---|---|---|
| `EPvPMatchFormat` | enum (`OneVOne`, `TwoVTwo`, `ThreeVThree`) | Shared by matchmaking and the GameMode's team-size logic. |
| `UPvPMatchmakingSubsystem` | `UGameInstanceSubsystem` | Client-side queue state machine: `SelectFormat(EPvPMatchFormat)`, `JoinQueue()`, `LeaveQueue()`, broadcasts `OnQueueStatusChanged`. Talks to matches through a small `IPvPMatchProvider` interface — for M1 the only implementation is `FPvPLocalMatchProvider` (session create/find via `OnlineSubsystemNull`, direct connect). **This interface seam is the explicit hook for skill-based matchmaking later** — a future `FPvPSkillBasedMatchProvider` drops in without touching the subsystem's public API or any calling UI code. Building the seam now costs almost nothing and is exactly the kind of thing worth doing from day one because the requirement doc already tells us it's coming. |
| `UPvPFormatPickerWidget` | `UUserWidget` (Blueprint-authored, thin C++ base if needed) | Three buttons (1v1/2v2/3v3) + "Find Match" + queue status text. Pure UI, built in UMG. |

**Online subsystem call:** M1 uses `OnlineSubsystemNull` (Epic's built-in, no external account/SDK needed) for session create/find, with direct-IP as the fallback connect path for local testing. **Recommendation, made here rather than left open:** do not integrate Steamworks or EOS for M1 — that's a real chunk of third-party SDK setup (app IDs, SDK download, platform config) that buys nothing for proving out the deathmatch + hit-reg + format-picker loop, and the `IPvPMatchProvider` seam above means swapping it in later doesn't touch game logic. If Daniel wants Steam-visible multiplayer in M1 specifically (e.g., for external playtesters), that's a scope addition — price it and kick it to studio-director rather than assume it.

## 3. Git Workflow

### 3.1 Branching model

Trunk-based, sized for a solo developer (revisit when the team grows):

- `main` — always compiles, always playable. Nothing lands here that doesn't meet its task's DONE WHEN.
- `feature/<short-slug>` — one branch per task from §4 (e.g. `feature/weapon-component`, `feature/lag-compensation`). Branch from `main`, merge back to `main` when done, delete the branch.
- No standing `dev`/`develop` branch — at this scale it's ceremony without payoff (nothing else is consuming an integration branch). Add one back if/when a second developer or a QA environment needs a stabilization buffer ahead of `main`.
- Merge via squash (keeps `main` history one commit per task, matches the task breakdown below) unless a task's history is itself worth preserving.

### 3.2 Git LFS setup

Binary/large asset types must go through LFS or the repo becomes unworkable within weeks. `.gitattributes` at repo root:

```
*.uasset filter=lfs diff=lfs merge=lfs -text
*.umap   filter=lfs diff=lfs merge=lfs -text
*.fbx    filter=lfs diff=lfs merge=lfs -text
*.png    filter=lfs diff=lfs merge=lfs -text
*.tga    filter=lfs diff=lfs merge=lfs -text
*.psd    filter=lfs diff=lfs merge=lfs -text
*.wav    filter=lfs diff=lfs merge=lfs -text
*.mp3    filter=lfs diff=lfs merge=lfs -text
*.ogg    filter=lfs diff=lfs merge=lfs -text
*.mp4    filter=lfs diff=lfs merge=lfs -text
*.exr    filter=lfs diff=lfs merge=lfs -text
*.ttf    filter=lfs diff=lfs merge=lfs -text
*.otf    filter=lfs diff=lfs merge=lfs -text
```

`.gitignore`: start from Epic's official UnrealEngine `.gitignore` (excludes `Binaries/`, `Intermediate/`, `DerivedDataCache/`, `Saved/`, `.vs/`, `*.VC.db`, etc. — these are all regenerated locally and must never be committed, LFS or otherwise). Do not hand-roll this list; Epic's is the canonical version and covers editor-version-specific junk that's easy to miss.

**Sequencing matters:** run `git lfs install` and commit `.gitattributes` **before** the first `.uasset`/`.umap` is ever added — LFS only tracks files matching the filter going forward, retrofitting it onto already-committed binaries requires a history rewrite. This is one of the first commands in Phase A below.
